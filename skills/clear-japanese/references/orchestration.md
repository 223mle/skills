# レビューの委譲と並列実行

執筆したエージェントに自分の文章をレビューさせない。書いたばかりの文章には書き手のバイアスがかかり、執筆時の思い込みをそのまま引き継ぐ。レビュワーには成果物とレビュー基準だけを渡し、執筆の経緯（構想メモ、それまでの会話）は渡さない。

委譲するときの設計原則は2つ。

1. **オーケストレーターは対象文書の本文を読まない**。本文を読むのはサブエージェントだけにして、オーケストレーターが受け取るのは原文引用付きの指摘までにする。長い文書を自分で読み込むと、指摘を統合する前にオーケストレーターのコンテキストが尽きる
2. **サブエージェントには安価なモデルを指定する**。判定基準は references に明文化されているので、検出・検証・修正の適用に高い知能は要らない

## 目次

1. 実行形態の選び方
2. モデルの指定
3. 並列レビューの手順（レビュー → 検証 → 統合）
4. 修正の適用

## 1. 実行形態の選び方

文章の規模と重要度でレビューの重さを変える。並列レビューはトークンを大きく消費するので、すべての文章に適用せず、価値が見合うときだけ使う。

1. **短い文章（目安2,000字まで）や途中稿** → 同一セッションで3パスを順に実行する（SKILL.md のレビューモード）。委譲は不要
2. **長い文章・複数ファイル・公開前の最終レビュー** → ファイルごと × 観点ごとのサブエージェントに委譲し、並列で実行する（このファイルの手順3）
3. **サブエージェント機能が使えない環境** → 直列で3パスを実行する。ただしパスごとに、成果物とそのパスの references ファイルだけを読み直す。他の作業の続きの流れでレビューしない

## 2. モデルの指定

- **レビュワー・検証・修正適用のサブエージェント**: 安価な小型モデルを指定する。執筆時点の推奨は、Claude Code なら Sonnet 5（Agent ツールの `model: "sonnet"`）、Codex なら gpt-5.6-luna
- **オーケストレーター**: セッションで選択中のモデルのまま。変えない
- モデルを指定する手段がない環境では、既定のモデルのまま起動してよい（ファイル分割と検証の仕組みは変えない）

## 3. 並列レビューの手順

### 3-1. ファイル × 観点でレビュワーを起動する

対象ファイルごとに、観点別レビュワー3体を起動する（5ファイルなら 3 × 5 = 15体）。各レビュワーは互いに独立で読み取りしかしないので、1回の呼び出しでまとめて並列に起動する。レビュワーに修正はさせず、指摘の収集だけをさせる。

| 観点 | 読む references |
|---|---|
| 構造 | structure.md |
| 語彙・文 | vocabulary.md と sentence.md |
| AIっぽさ | ai-smell.md |

語彙・文のレビュワーは references を2つ読むが、指摘の layer は「語彙」「文」を個別に付ける（HTML レポートのスキーマに合わせる）。

各レビュワーへの指示には、次の5要素を必ず入れる。曖昧な指示は、観点の重複と抜け、そして水増しされた指摘を生む。

1. **目的**: どの層の問題だけを検出するか
2. **出力形式**: 指摘ごとに「原文引用 / 修正案 / 理由 / layer / 重大度 / 確信度」
3. **参照ファイル**: 対象文書のパスと、その観点の references ファイルのパス
4. **指摘のバー**: references のルールに明確に違反する箇所だけを指摘する。「指摘なし」を正常な結果として認める
5. **境界**: 他の層に踏み込まない。文書の主張・内容の正誤に意見しない

指示のテンプレート（語彙・文の観点の例）:

```
次の文書をレビューし、指摘の一覧だけを最終メッセージで返してください。文書の編集はしないでください。

- 目的: 語彙・文の層の問題だけを検出する。<このスキルの base directory>/references/vocabulary.md と references/sentence.md を読み、そのルールとテストで診断する
- 対象: <文書のパス>
- 出力形式: 指摘ごとに「原文引用（一字一句そのまま）/ 修正案 / 理由（違反したルール・テストの名前）/ layer（語彙 または 文）/ 重大度（高・中・低）/ 確信度（0〜100。100=確実に問題）」
- 指摘のバー: references のルールに明確に違反する箇所だけを指摘する。ルール名を挙げられない指摘、意味も読みやすさもほぼ変わらない言い換え、好みの提案は出さない。確信度80未満の指摘は自分で捨てる。問題が見つからなければ「指摘なし」とだけ返す。それは正常な結果であり、無理に件数を作らない
- 境界: 構造・AIっぽさには触れない。内容の正誤にも意見しない。文書の意味を変える指摘は、確信度を下げて出す
```

「指摘のバー」の一段落が収束性の要になる。レビュワーは、指摘を頼まれれば健全な文章にも好みレベルの言い換えを出してしまう。この一段落が無いと、同じ文書に何回レビューをかけても毎回新しい「言い換え」が湧き続ける。

### 3-2. ファイル単位の検証エージェントで指摘を潰す

3観点のレビュワーが返した指摘を、ファイルごとに1体の検証エージェント（同じく安価なモデル）に渡して反証させる。レビュー段階のバーだけでは落としきれない誤検出を、ここで潰す。

検証エージェントへの指示のテンプレート:

```
次の文書へのレビュー指摘を検証してください。文書の編集はしないでください。

- 対象: <文書のパス>
- 参照: <このスキルの base directory>/references/ の structure.md / vocabulary.md / sentence.md / ai-smell.md（指摘が挙げるルールの実在確認に使う）と html-report.md（出力スキーマ）
- 指摘リスト: <このファイルへの3観点分の指摘をそのまま貼る>
- 手順: 指摘ごとに反証を試みる。次のどれかに当てはまったら落とす:
  1. 原文引用が文書に実在しない
  2. 挙げられたルールが references に実在しない、または当該箇所は実際にはそのルールに違反していない
  3. 修正案が書き手の主張・事実関係・文体を変えている
  4. 修正案を適用しても読みやすさが実質変わらない（言い換えにすぎない）
- 同じ箇所への指摘は1つに統合する（層をまたぐ場合は重大度の高い方に寄せる）
- 出力: 生き残った指摘だけを、html-report.md の findings スキーマの JSON 配列で最終メッセージに返す（id はこのファイル内の連番、重大度順）。全部落ちたら空配列 [] を返す
```

### 3-3. 統合して提示する

オーケストレーターは、検証済みの findings 配列をファイルごとに受け取り、`doc` / `date` / `summary`（総評: 最も直す価値がある問題は何か）を付けて JSON にまとめ、SKILL.md の「指摘の出力形式」に従って提示する（既定は HTML レポート。複数ファイルのときはファイルごとに1レポート生成する。references/html-report.md に従う）。チャットには全ファイル合算の件数サマリーと総評だけを書く。修正の採否は書き手（人間）が決める。レビューは判断材料の提供であって、決定ではない。

## 4. 修正の適用

並列のレビュワーに修正までさせない（指摘の採否を人間が判断する前に文書が書き換わってしまう）。修正を頼まれたら、またはHTML レポートの「レビュー反映指示」が貼られたら、**ファイル単位で**適用エージェント（安価なモデル）を並列に起動する。別ファイルへの書き込みは衝突しないので並列でよい。同一ファイル内は1体が構造 → 語彙 → 文 → AIっぽさの順に直列で適用する（構造を後から直すと文レベルの修正が無駄になる）。

各適用エージェントへの指示に入れるもの:

- 対象ファイルのパス
- 採用された指摘のリスト（修正後テキスト付き）。採用されなかった指摘は渡さない
- ユーザーが編集した修正後テキストは一字も変えずに使う（references/html-report.md の反映指示の処理に従う）
- 指摘の対象箇所以外を書き換えない
