# Clear Japanese — レビュワーを意識した日本語

## 目的

LLM の日本語が分かりにくい原因は3つの層に整理できる。このスキルは3層すべてを扱う。

1. **語彙の層**: 読んでも具体的な意味が思い浮かばない語を使ってしまう。例: 英語術語の直訳（false rejection を「誤った拒否」と書く。原語を知らない読者には何のことか分からない）、中身を説明しないまま使う比喩（「凍結」と書くが、実際には「ファイルを zip に固めて変更不可にする」ことを指している）
2. **文の層**: 英語の文の組み立てをそのまま日本語に写してしまう。例: 「この機能は〜を可能にします」のような人でない主語、1文への詰め込み、誰の動作か分からない文
3. **構造の層**: 結論が最後まで出てこない。読者の疑問に答えない情報が混ざる。「組織の問題」のような分類名だけのラベルで項目を言い切り、中身を書かない

目指す状態は「**具体的かつ概要**」。可能な限り短く、要点を具体的にはっきり言う。

## 3つの判定テスト

「この語は禁止」という語のリストで機械的に判定せず、疑わしい箇所に次のテストをかける。

1. **復元テスト**（語彙・文の層）: この語・この文だけを読んで、読者は「誰が・何を・どうする」を具体的に思い浮かべられるか。思い浮かべられないなら、「誰が・何を・どうする」が分かる文に書き直す。語を残したい場合は、その語が指す具体的な操作を初出で説明してから使う（例: 「zip に固めて変更不可にする。以降これを凍結と呼ぶ」）
2. **新情報テスト**（文の層）: この文は、文書が扱う対象について新しい情報を伝えているか。文書の進行を案内するだけの文（「ここまで見てきたように」「次に具体例を見ていきましょう」）は、削除するか、対象についての情報に書き換える
3. **疑問応答テスト**（構造の層）: 直前の見出し・文を読んだ読者に浮かぶ疑問（それは何？なぜ？どうやって？）に、この段落は答えているか。どの疑問にも答えていない段落・データは削除の候補にする

## ルールの正本（references/）

層ごとに分かれている。執筆前・レビュー時に該当ファイルを読む。

- [references/vocabulary.md](references/vocabulary.md) — 語彙の層: 直訳の名詞句を文に書き直す、比喩は中身を説明してから使う、ぼかし語の置き換え、対義語のペア、要注意ワード
- [references/sentence.md](references/sentence.md) — 文の層: 人でない主語、一文一義、隠れた主語、冗長表現、助詞
- [references/structure.md](references/structure.md) — 構造の層: 結論先行、ラベルへの中身の入れ方、導入の組み方、並列の整理、リスト・表・文章の使い分け、書く前に決める3点
- [references/ai-smell.md](references/ai-smell.md) — AIっぽさ: 対比構文、決め台詞、保険表現、文の長さのリズム、誠実さのブレーキ（修正しすぎの防止）
- [references/orchestration.md](references/orchestration.md) — レビューの委譲と並列実行: 別エージェントへの委譲、観点別レビュワーの並列起動、指摘の検証と統合
- [references/html-report.md](references/html-report.md) — レビュー結果の HTML レポート: 指摘 JSON のスキーマ、生成コマンド、採用/却下の反映指示の処理

## モードの選択

- ユーザーがこれから書く・書きながら直すことを求めている → **執筆モード**
- 既存の文章への指摘・修正を求めている → **レビューモード**
- 迷ったらレビューモード（既存の文章があるなら、まず現状を診断する）

## 執筆モード

1. 書き始める前に、次の3点を1〜2文ずつ決める。曖昧なまま書き始めない
   1. **読後アウトプット**: 読者が持ち帰るもの
   2. **解消したい課題**: 誰のどんな課題を解くのか
   3. **想定読者と前提知識**: どこまでを前提知識とするか
2. references/structure.md を読み、結論先行の構造を組む
3. references/vocabulary.md と references/sentence.md を読んでから本文を書く
4. 書き終えたらレビューする。サブエージェントが使えるなら、別エージェントに委譲する（references/orchestration.md を読む。書いた本人がレビューすると、執筆時の思い込みを引き継ぐ）。使えなければ、レビューモードの4パスで自己レビューして修正する

文体（です・ます / だ・である）は、対象文書やそのリポジトリの既存文書に合わせる。指定がなければ、です・ます調にする。

## レビューモード

まず実行形態を選ぶ。判断基準と委譲の手順は references/orchestration.md にある。

1. **短い文章（目安2,000字まで）・途中稿** → このセッションで下の4パスを順に実行する
2. **長い文章・公開前の最終レビュー** → 観点別のサブエージェント4体に委譲して並列でレビューし、指摘を検証・統合する（references/orchestration.md の手順に従う）
3. **自分が書いた直後の文章** → できるだけ別エージェントに委譲する

パスを4回に分けて全文を見る。1回で全部見ようとすると、構造の問題（もっとも直す価値が高い）を見落とす。

1. **構造パス**: references/structure.md を読み、結論の位置・中身のないラベル・疑問応答テストで診断する。構造の修正は文の修正より先に行う（構造を後から直すと、文レベルの修正が無駄になる）
2. **語彙パス**: references/vocabulary.md を読み、復元テストで用語・比喩・ぼかし語を診断する
3. **文パス**: references/sentence.md を読み、人でない主語・主張の詰め込み・主語の消失を診断する
4. **AIっぽさパス**: references/ai-smell.md を読み、対比構文・決め台詞・保険表現・リズムを診断する

### 指摘の出力形式

修正を直接適用するよう頼まれていない限り、**HTML レポートで提示するのが既定**。references/html-report.md を読み、指摘の JSON を書いて生成スクリプトを実行し、`open` で表示する（テンプレート HTML 自体は読まない）。ユーザーは HTML 上で指摘ごとに採用/却下を選び、修正案を直接編集して、結果をチャットに貼り戻す。貼り戻された「レビュー反映指示」の処理も references/html-report.md に従う。

ブラウザを開けない環境・ユーザーがテキストを求めたとき・指摘が2件以下のときは、次の Markdown 形式で提示する。

```
### 指摘 1（重大度: 高 / 層: 語彙）

**修正前:**
> 元の文章

**修正後:**
> 改善した文章

**理由:** なぜ読者に伝わらないか（どのテストに失敗したか）
```

重大度の基準:
- **高**: 読者が意味を取り違えるか、書き手に質問しないと先に進めない
- **中**: 意味は取れるが、読み直しが必要になる
- **低**: 意味は伝わるが、AIっぽさ・リズムの問題が残る

### レビューの心得

- 指摘には必ず修正案を付ける。「分かりにくい」とだけ言わない
- 書き手の主張・事実関係を変えない。推測で書かれたことを断定に変えない（references/ai-smell.md の「誠実さのブレーキ」を守る）
- 文書全体の文体・トーンは維持する。個性やユーモアを削らない
- 明らかな誤字脱字は重大度に関係なく指摘する
